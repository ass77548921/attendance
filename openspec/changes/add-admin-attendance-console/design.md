## Context

本次需求是完整定義管理後台能力，涵蓋出缺勤查詢、人工修正與稽核、上下班規則設定、郵件發送設定、通知收件人管理、人員帳號管理。既有規格雖涵蓋部分管理端場景，但尚未完整描述「人工修正必填理由且保留審計軌跡」與「SMTP/寄件資訊可由後台維護」等關鍵營運需求。

變更涉及多個模組（出勤、規則、通知、認證），屬於跨能力擴充，需要先在 spec 層建立一致契約，再由後端 API 與後台前端分階段落地。

## Goals / Non-Goals

**Goals:**
- 提供管理員可查詢與手動修正出缺勤資料，且修正操作可追溯（修改人、時間、理由、前後差異）。
- 提供可管理的上下班規則設定（上班時間、下班時間、遲到容忍、工時門檻）。
- 提供郵件發送設定管理（帳號、密碼、主旨、寄件名稱）與測試驗證。
- 提供通知收件人管理與人員帳號管理的完整後台 API 契約。
- 即使目前後端無完整 API，也可依規格拆解任務逐步實作。

**Non-Goals:**
- 本次不定義前端 UI 細節（版型、元件風格、互動動畫）。
- 本次不更動核心打卡演算法（僅擴充管理端操作與設定入口）。
- 本次不引入外部 IAM 平台（沿用既有 JWT/角色模型）。

## Decisions

1. 以 spec-first 方式定義管理後台能力，後端 API 與前端後台依同一契約開發。
- 理由：可在「後端尚未齊備」情況下先穩定需求範圍與驗收標準。
- 替代方案：先開發 API 再補規格。未採用，避免需求漂移與重工。

2. 人工修正出勤採「強制理由 + 稽核紀錄」模型。
- 理由：出缺勤資料涉及人資與法遵，需可追溯。
- 替代方案：只更新主表不留審計。未採用，稽核風險過高。

3. 郵件設定採「參數集中管理 + 憑證安全儲存 + 測試發送」流程。
- 理由：SMTP 常由營運調整，需可配置且可驗證。
- 替代方案：僅用環境變數手動改。未採用，維運效率低且容易誤設。

4. 權限邊界維持 ADMIN/EMPLOYEE，但補齊後台端點授權要求。
- 理由：最小變更延續既有模型，同時滿足後台保護需求。
- 替代方案：新增細粒度 RBAC。未採用，超出本次範圍。

## Risks / Trade-offs

- [人工修正 API 破壞原始出勤一致性] -> Mitigation: 強制寫入審計紀錄，並對修改欄位加白名單限制。
- [SMTP 密碼明文保存風險] -> Mitigation: 使用加密儲存或秘密管理機制，回應 DTO 永不返回明文。
- [規則設定誤改造成大量通知異常] -> Mitigation: 增加設定驗證與測試發送，必要時加入變更確認機制。
- [需求跨模組導致交付延遲] -> Mitigation: 依 capability 切分任務，先交付可用最小 API 再擴充。

## Migration Plan

1. 先落地規格檔（新增 capability + 修改既有 capability）。
2. 新增資料模型：出勤修正審計表、郵件設定表（含敏感欄位保護）。
3. 分批實作 API：出勤修正/規則設定/郵件設定/收件人管理/帳號管理。
4. 補整合測試與權限測試，確認核心打卡流程無回歸。
5. 以 feature toggle 或分批上線策略導入後台功能。

## Open Questions

- 郵件設定是否允許多組 profile（例如正式/測試）同時存在？
- 出勤人工修正是否需要二次覆核流程，還是單一管理員即可生效？
- 帳號管理是否需要密碼重設流程與強制首次登入改密碼？
