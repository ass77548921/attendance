## Context

現況後台登入頁允許輸入任何有效帳號密碼進行登入，但規格未明確定義「員工帳號嘗試登入後台」的處理方式與提示文案，導致使用者可能登入後才被其他權限機制擋下，體驗不一致且容易混淆。

本次變更聚焦於「登入當下」即完成角色可管理性判斷：ADMIN 可正常進入後台；EMPLOYEE 不可進入，且必須在登入介面看到可理解且可追蹤的錯誤提示。

## Goals / Non-Goals

**Goals:**
- 明確規範後台登入對 EMPLOYEE 帳號的拒絕行為與文案。
- 確保 EMPLOYEE 帳號不會被導向任何 `/admin/*` 管理頁。
- 保持 ADMIN 既有登入成功路徑與導向不變。
- 統一前後端可識別的拒絕語意，避免前端只能靠模糊字串判斷。

**Non-Goals:**
- 不調整一般員工端（非後台）登入流程。
- 不引入新的角色模型或 RBAC 架構調整。
- 不改動後台其他功能頁的授權規則（僅處理登入入口行為與提示）。

## Decisions

### 1) 在登入流程加入角色可管理性檢查
- 決定：以後台登入流程為界，若帳號角色為 EMPLOYEE，登入請求應回傳可辨識的拒絕結果，前端停留在登入頁並顯示固定提示。
- 理由：在入口即阻擋可避免「先登入成功再被逐頁 403」的割裂體驗。
- 替代方案：前端登入成功後解析 role 再主動登出並提示；此方案依賴前端實作時序，且安全語意較分散，因此不採用。

### 2) 錯誤語意採可機器判斷形式
- 決定：後端登入拒絕 EMPLOYEE 管理登入時，提供穩定錯誤碼/錯誤類型（例如 `EMPLOYEE_ACCOUNT_NO_ADMIN_ACCESS`），前端再對應顯示文案「此帳號為員工帳號，無法管理後台」。
- 理由：降低文案變更造成行為誤判風險，並便於測試與國際化。
- 替代方案：只傳一般 401/403 與自然語言訊息；但可測性與穩定性較差。

### 3) 保持 ADMIN 登入成功路徑不變
- 決定：ADMIN 登入成功仍維持既有 token 儲存與導向 `/admin/attendance`。
- 理由：最小改動，避免不必要回歸風險。

## Risks / Trade-offs

- 風險：前後端對錯誤碼定義不同步，造成提示失效。
  - 緩解：在 spec 中固定錯誤語意，並加入端到端測試案例。
- 風險：若後端暫時無法提供專屬錯誤碼，前端需 fallback 判斷訊息。
  - 緩解：保留臨時 fallback，但在任務中標記為過渡策略。
- 取捨：在登入端就拒絕 EMPLOYEE，會讓部分「共用登入端點」設計更嚴格。
  - 理由：可提升管理後台邊界清晰度，符合本次需求。

## Migration Plan

1. 更新 `admin-operations-console` 規格，加入員工帳號登入後台的拒絕情境與顯示文案要求。
2. 後端登入流程補上 role-based 拒絕語意（HTTP 狀態與錯誤碼）。
3. 前端登入頁調整錯誤處理：針對該錯誤碼顯示「此帳號為員工帳號，無法管理後台」，且不導向管理頁。
4. 加入測試：
   - ADMIN 正常登入成功
   - EMPLOYEE 後台登入被拒且顯示指定訊息
   - 錯誤帳密維持原有錯誤訊息
5. 逐步部署並觀察登入錯誤事件，確認員工誤登入提示可被正確辨識。

## Open Questions

- 若系統未來支援多語系，該提示文案是否改為 i18n key 管理？
