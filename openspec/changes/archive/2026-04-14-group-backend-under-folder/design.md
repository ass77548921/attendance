## Context

目前儲存庫將後端執行程式與根目錄層級的專案操作放在同一個平面工作區。未來若加入前台與後台模組，結構會變得模糊：貢獻者可能把新檔案放在不一致的位置、指令入口不清楚，CI/CD 對路徑的假設也可能互相衝突。

此變更的目標是在不改變既有執行行為與 API 契約的前提下，建立明確的後端容器目錄。設計重點是只調整路徑、腳本與文件，將遷移風險降到最低，避免觸及商業邏輯。

## Goals / Non-Goals

**Goals:**
- 在儲存庫內建立明確的後端根目錄邊界。
- 保留既有後端行為、API 回應與資料庫互動。
- 路徑遷移後，本地開發與容器流程可持續正常運作。
- 讓未來前台/後台模組放置位置清楚且不混淆。

**Non-Goals:**
- 不進行 API 契約重設計，不改變 endpoint 行為。
- 不重設計資料庫 schema 或 migration 邏輯。
- 本次不實作任何前台/後台功能。
- 除非工具必要，不進行大規模 backend package 命名重構。

## Decisions

1. 採用 `backend/` 作為後端容器目錄。
- 理由：用一個明確資料夾邊界解決儲存庫層級混淆，且改動最小。
- 替代方案：維持後端在根目錄，只補文件規範。未採用，因為純文件規範容易隨時間偏移，無法形成硬性邊界。

2. 移動專案檔案時保留 Java package 命名空間（`com.attendance`）不變。
- 理由：避免程式碼層級重構，降低執行風險。
- 替代方案：同步調整 package 階層。未採用，因為影響面過大，超出本次結構調整必要範圍。

3. 所有操作入口統一更新為 `backend/` 路徑。
- 理由：建置、測試、Docker 與文件需要一致，避免 onboarding 失敗。
- 替代方案：先加相容包裝、延後完整遷移。未採用，避免長期維護雙路徑造成複雜度。

4. 將本次視為具驗證關卡的遷移作業。
- 理由：路徑變更可能在 CI 與 Compose 中產生隱性故障，需在合併前進行顯式驗證。
- 替代方案：僅靠人工臨時驗證。未採用，回歸風險較高。

## Risks / Trade-offs

- [建置腳本路徑失效] -> 緩解：更新 Gradle/Compose 參考路徑，並以完整測試與 Compose 啟動驗證。
- [CI pipeline 對根目錄路徑有既有假設] -> 緩解：盤點並更新 workflow 內路徑參考，必要時執行 pipeline dry-run。
- [遷移期間開發者認知混亂] -> 緩解：同一變更內同步更新 README 與本地設定文件。
- [相對路徑工具行為不一致] -> 緩解：統一指令範例寫法，並明確標示工作目錄。

## Migration Plan

1. 建立 `backend/` 目錄並移入後端專案檔案。
2. 更新 Docker/Compose 設定與相關腳本，改用新相對路徑。
3. 更新 README 與本地設定指引，反映新專案結構。
4. 執行後端測試與容器啟動驗證。
5. 合併時附上回滾策略：若任一環境無法解析新路徑，則回退結構遷移 commit。

## Open Questions

- 根目錄的 `docker-compose.yml` 是否保留在 root 並參考 `backend/`，還是移入 `backend/` 並在 root 提供包裝入口？
- 現有 CI workflow 是否依賴 root 層級 Gradle wrapper 路徑，需不需要相容 symlink 或腳本？
- 未來前台與後台模組資料夾命名（如 `frontend/`、`admin/`）是否要在此變更先行保留？
